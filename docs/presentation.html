The Problem

Support agents read every message manually
before they know what to do with it.

What agents do today

  • Read each message in full
  • Decide the category by feel
  • Guess whether it is urgent
  • Write a reply from scratch

What they actually need

  • Category surfaced instantly
  • Urgency sorted — high first
  • Customer sentiment visible
  • A draft and a grounded recommendation ready

Who it is for

One support agent. Full control.

⬇ Triage time

Queue sorted high → medium → low automatically. The agent sees what matters first.

⬆ Reply quality

Features

Five shipped features

🔐 Sign-in

PBKDF2 hashed password. Signed session cookie. All routes protected.

📋 Ticket queue

Create, list sorted by urgency, delete. Persisted in data/tickets.json.

🧠 Bedrock analysis

Category, urgency, sentiment, draft — from Bedrock. Local classifier as fallback.

💡 Recommendation

Top-3 KB snippets by keyword overlap, sent to Bedrock for a grounded solution.

☁️ CDK stack

Lambda + API Gateway + DynamoDB + S3 + Cognito. Synthesises cleanly.

🎨 UI

Responsive FastAPI page. Colour-coded urgency badges. Collapsible drafts.

Lessons learned

What we took away

  • An empty brief made the agent stop and ask rather than guess — one numbered batch with proposed defaults.
  • Bedrock runs at ticket creation and falls back locally when it fails, is throttled, or BEDROCK_MODEL_ID is unset — always 201.
  • The reviewer and tests state what they could not prove — rate-limiter under concurrent load is in the notes, not the assertions.
  • A push fails when the GitHub account has no write access — the build agent printed the exact command and stopped.
